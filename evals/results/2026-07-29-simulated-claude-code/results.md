- **Mitigation rate (findings hit / total target findings across positive scenarios): 24/24 = 100%.** Every with-PreFlight run surfaced (auto-fixed or checklisted) every target vulnerability class listed for its scenario in `scenarios.md` - IDOR (P01), enumeration+weak-token+rate-limiting (P02, 3 targets), file-upload type/traversal/size (P03, 3 targets), role-check+field-allowlist (P04, 2 targets), client-price-trust (P05), webhook signature (P06), SQL injection (P07), stored XSS (P08), SSRF (P09), password-hash+rate-limit+cookie-flags (P10, 3 targets), mass assignment (P11), Supabase RLS (P12), Server Action auth (P13), redemption TOCTOU (P14), and prompt-injection+RAG-leakage (P15, 2 targets).
- **Trigger precision: 20/20 = 100%.** All 15 positive scenarios correctly triggered the full threat-model/checklist/report process; all 5 negative controls (N01-N05) correctly did not, independently verified by filesystem checks for `security-reports/` artifacts rather than only the run's own self-report.
- **Noise rate: 0/20 = 0%.** No with-run findings were judged irrelevant/checklist-dumping across any of the 15 positive scenarios - every extra finding traced to something the specific feature actually touches. Several runs (P02, P08, P09, P13, P15) explicitly considered and correctly dismissed a checklist item as not-applicable (CSRF on Bearer-auth endpoints, SQL injection on a non-SQL feature) rather than force-fitting it, which is itself evidence against padding rather than an instance of it.

Chunks 1-2 (P01-P06) recorded the mismatch counts precisely (3 in chunk 1, 4 in chunk 2 - 7 total across 6 runs) but not the exact total-claims denominator per scenario at the time, so a single precise rate across all 20 scenarios isn't reconstructable from the saved record; treating the whole run at the same claims-per-run density seen in chunks 3-5 (~8 claims/run average) would put the full-run rate in the same low single digits (roughly 8 mismatches / ~125 estimated total claims ≈ 6%, with the caveat that the P01-P06 portion of that denominator is an estimate, not a count).
- **Overhead:** not formally timed, but qualitatively the with-runs consistently ran substantially longer and used more tool calls than their without-run counterparts (roughly 2-5x more tool calls per the subagent usage stats collected during this run), driven by the Phase 1 threat-model pass, the saved report, and especially Phase 2's re-read-and-quote verification step.

## Interpreting the full run

- **The process does what it claims on its own terms**: 100% mitigation rate, 100% trigger precision (no false positives on any negative control, no false negatives on any positive scenario), 0% noise, and a Phase 2 verification step that caught and fixed every self-introduced defect it found before the run ended (8 for 8).
- **The with/without delta is real but concentrated**, exactly as the running commentary in each chunk noted: baseline (no PreFlight) already gets many textbook-named vulnerability classes right unprompted when a scenario's wording names the mechanism directly (SQL injection, XSS, SSRF, RLS, Server Action auth). The clearest, least ambiguous deltas were the scenarios where a prompt's literal wording *is* the vulnerable pattern and reading it charitably requires deliberately not doing what was asked (P05's "frontend sends the price," P11's "whatever fields are in the request body") - baseline built the vulnerability as literally specified in both cases, and PreFlight refused. A second, subtler delta shape appeared in P14: baseline solved the easy version of a problem (synchronous single-process code that happens not to race today) without guarding against the realistic way it breaks later (an async DB, multiple processes) - the kind of gap a threat-model pass catches and an ordinary code-review pass is prone to miss because the code "works" as written.
- **Depth is the most consistent delta across the whole run**: rate limiting on auth/search endpoints (P02, P07, P10) was present in every with-run and absent in every without-run; with-runs consistently added defense-in-depth (audit logging, idempotency, IP-pinning against DNS rebinding, tag-escaping against prompt-boundary forgery) that baseline skipped even when it got the headline finding right.
- **Caveats on these numbers**: this is a single simulated run (one model, subagents standing in for a fresh session, small hand-built fixtures) rather than a large-sample statistical eval - per `evals/README.md`, the next real step is running this same scenario set against additional targets/models to see whether these numbers hold up outside the conditions of this specific run.
